# java-movies-hub
MovieHub: кинотеатр у вас в браузере
Представьте, что небольшая киностудия решила запустить сервис MovieHub — простой API для управления любимыми фильмами.
Менеджер продукта пришёл к вам с такой концепцией:
«У пользователей должна быть возможность добавлять фильмы в список, получать список фильмов, искать их по ID и удалять. Хранение данных — в памяти, база пока не нужна. Формат обмена — JSON».
Проект небольшой, зато практичный: чёткие правила, понятные ответы сервера и реальные HTTP-запросы. Задача — реализовать этот API.
Разработка через тестирование
Чтобы такой сервис был надёжным, важно зафиксировать все правила: какие ответы должен вернуть сервер и как он должен вести себя в разных ситуациях. Для этого будем использовать подход TDD (Test Driven Development) — разработка через тестирование.
Суть подхода проста:
Сначала пишем тест, который описывает поведение API. Он падает, так как реализации ещё нет.
Потом добавляем минимальный код, чтобы тест проходил.
Затем улучшаем код, не ломая тесты.
Так вы будете двигаться шаг за шагом: от пустого списка фильмов к добавлению, поиску, удалению и обработке ошибок. В итоге у вас получится не только работающий сервер, но и набор тестов, которые будут выполнять роль «живой документации».
Теперь перейдём к спецификации, которую составил бизнес-аналитик компании после общения с заказчиком.
Спецификация
Общие правила
Сервер запускается на localhost:8080.
Формат запросов и ответов — JSON, кодировка UTF-8.
Ответы содержат корректные коды статусов и заголовки (как минимум Content-Type).
Данные хранятся в памяти (например, в HashMap).
Функциональные требования
Эндпоинты:
Получение всех фильмов
Эндпоинт — GET /movies.
Ответ:
Код статуса — 200 OK.
Если фильмов нет — вернуть пустой JSON-массив.
Если фильмы есть — вернуть массив фильмов.
Добавление фильма
Эндпоинт — POST /movies.
Тело запроса, содержит поля:
title — не пустая строка, длина ≤ 100 символов.
year — число от 1888 (год самого раннего из сохранившихся фильмов) до текущий год + 1.
Ответ:
  
Если фильм успешно добавлен:
Код статуса — 201 Created.
Тело — JSON созданного фильма с присвоенным ID.
Если произошла ошибка валидации:
Код статуса — 422 Unprocessable Entity.
Тело — объект с информацией об ошибке, содержит следующие поля:
error — короткое описание ошибки, например, Ошибка валидации.
details — массив строк с деталями проблемы, например:

["название не должно быть пустым", "год должен быть между 1888 и 2026"] 
Если был получен запрос с неправильным значением заголовка Content-Type:
Код статуса — 415 Unsupported Media Type.
Получение фильма по идентификатору
Эндпоинт — GET /movies/{id}.
Если фильм найден:
Код статуса — 200 OK.
Тело ответа — объект, представляющий найденный фильм.
Если фильм не найден:
Код статуса — 404 Not Found.
Тело ответа — сообщение об ошибке, например, Фильм не найден.
Если ID, указанный в пути запроса, не число:
Код статуса — 400 Bad Request.
Тело ответа — сообщение об ошибке, например, Некорректный ID.
Удаление фильма
Эндпоинт — DELETE /movies/{id}.
Если удалён:
Код статуса — 204 No Content.
Если фильм не найден:
Код статуса — 404 Not Found.
Фильтрация по году выпуска
Эндпоинт — GET /movies?year=YYYY.
Если параметр строки запроса (year) указан и он корректный:
Код ответа — 200 OK.
Тело ответа — список фильмов, соответствующих указанному году.
В других случаях — ошибка:
Код ответа — 400 Bad Request.
Тело ответа — сообщение об ошибке, например, Некорректный параметр запроса — 'year'.
Нефункциональные требования
Чёткая структура кода (разделение моделей, хранилища, сервера).
Обработка ошибок с корректными кодами ответа.
Тесты на все эндпоинты (успешные и негативные сценарии).
Список проверок
Спецификация даёт нам общее представление о том, как должен работать сервис: какие есть эндпоинты, какие коды ответа возвращать, какие ошибки обрабатывать. Но для работы по TDD этого недостаточно — нужны конкретные проверки, которые можно превратить в тесты.
По сути, это перевод «язык аналитика» на «язык разработчика»: вместо общих правил формулируем простые и понятные сценарии — что отправляем на сервер и какой результат должны получить.
Так на основе спецификации получается краткий список проверок. Именно по нему вы будете писать тесты и шаг за шагом реализовывать API:
GET /movies
возвращает пустой список, если нет фильмов;
возвращает список с ранее добавленными фильмами.
POST /movies
добавляет фильм при корректных данных;
возвращает ошибку при пустом title;
возвращает ошибку при слишком длинном title (> 100 символов);
возвращает ошибку при неверном year (меньше 1888 или больше текущего года + 1);
возвращает ошибку при неправильном Content-Type;
возвращает ошибку при некорректном JSON.
GET /movies/{id}
возвращает фильм по существующему id;
возвращает ошибку, если фильм не найден;
возвращает ошибку, если id не число.
DELETE /movies/{id}
удаляет фильм по существующему id;
возвращает ошибку, если фильм не найден;
возвращает ошибку, если id не число.
GET /movies?year=YYYY
возвращает фильмы указанного года;
возвращает пустой список, если фильмов с таким годом нет;
возвращает ошибку, если параметр year не число.
Общие
все успешные ответы содержат Content-Type — application/json; charset=UTF-8;
ошибки возвращают объект с полем error (и при необходимости details);
при неподдерживаемом HTTP-методе возвращается 405 Method Not Allowed.
TDD учит думать о контрактах: «что должен получить клиент». Для REST это не только тело ответа, но и метод, путь, код статуса, заголовки и структура ошибок. В следующем уроке вы пройдёте по стандартному в TDD циклу:
Red (красный) — сначала пишем тест, который описывает ожидаемое поведение системы, и убеждаемся, что он падает (ведь кода ещё нет).
Green (зелёный) — пишем минимальную реализацию, чтобы тест прошёл.
Blue/Refactor (синий/рефакторинг) — улучшаем код, сохраняя зелёные тесты.
